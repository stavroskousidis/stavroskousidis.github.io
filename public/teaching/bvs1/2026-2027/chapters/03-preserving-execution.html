3  Preserving Execution

Wintersemester 2026/2027

Author
Affiliation

Stavros Kousidis

ICCT

Checkpoint 1 is intentionally modest:

I have a process.

Before a process can exist as an operating-system abstraction, the system needs one simpler capability: execution must be able to stop and later continue.

This chapter develops only the machine state needed to make that idea visible.

3.1 1. From “run” to “continue later”

The current Hello BVS1 program starts and then follows one continuous control flow.

Now imagine:

do_first_thing();

process_yield();

do_second_thing();

The intended behaviour is:

  1. execute do_first_thing();
  2. enter process_yield();
  3. let the kernel regain control;
  4. later resume the process;
  5. continue with do_second_thing().

The process must therefore retain enough machine state to preserve its continuation.

Conceptually, execution state includes:

  • where execution should continue;
  • register values that are required to survive;
  • the current stack position;
  • the stack contents themselves.

For the first checkpoint, we deliberately exploit normal C function-call rules so that the saved context stays small and understandable.

3.2 2. Return addresses make continuation visible

Consider:

void first(void)
{
    second();
    third();
}

A machine-level function call must know both where to go and where to return afterwards.

RISC-V uses the register ra as the return-address register.

At a conceptual level:

call second
    ↓
remember continuation in ra
    ↓
execute second
    ↓
ret
    ↓
continue using ra

The exact instruction encoding is not important here.

The relevant insight is that a continuation is represented by machine state.

3.3 3. Why a stack is needed

Nested calls require values to survive while other functions execute.

The stack provides storage whose lifetime follows nested function calls.

RISC-V software conventionally uses sp as the stack pointer, and the stack grows toward lower addresses.

If two independent executions have different stacks, they also need different saved values of sp.

For example:

execution A: sp = 0x81003f80
execution B: sp = 0x81007f40

Restoring B’s registers but accidentally retaining A’s stack pointer would cause B to use the wrong stack.

The stack pointer is therefore part of the context that must be preserved.

3.4 4. The calling convention reduces what we need to save

A normal C function call does not promise that every general-purpose register is unchanged afterwards.

The calling convention distinguishes, among other categories:

  • caller-saved registers — the caller must preserve them if it needs them later;
  • callee-saved registers — the called function must restore them before returning.

RISC-V names the callee-saved general-purpose registers s0 through s11.

For a cooperative context switch that occurs at a normal function-call boundary, we can exploit that contract.

A minimal saved context can therefore contain:

ra
sp
s0 ... s11

The reason for saving ra here deserves care. In the general ABI it is not a callee-saved register. In the context-switch routine it is saved because it identifies the continuation to which the restored context should return.

This is not yet a full interrupt or trap frame. Later preemption occurs at an asynchronous boundary and requires different handling.

3.5 5. Represent the saved context in C

A compact representation is:

struct context {
    uint64_t ra;
    uint64_t sp;
    uint64_t s[12];
};

The exact final layout must agree with the assembly offsets used by the context-switch scaffold.

The important conceptual distinction is:

A context is saved execution state. It is not yet the whole process.

The structure simply answers:

Where, on which stack, and with which preserved register values can this execution continue?

3.6 6. The narrow assembly boundary

A simplified context switch can be read as:

switch_context:
    sd ra, 0(a0)
    sd sp, 8(a0)

    ld ra, 0(a1)
    ld sp, 8(a1)
    ret

The calling convention passes:

a0 → address of context to save
a1 → address of context to restore

The complete scaffold also preserves the callee-saved s registers.

The learning target is not to reproduce the whole routine from memory.

The important sequence is:

  1. store the current continuation and stack position into one context;
  2. load another context’s continuation and stack position;
  3. execute ret;
  4. continue according to the restored ra on the restored stack.

This is the key conceptual moment:

The final ret returns into the restored context, not necessarily to the code that called the switch most recently in wall-clock time.

3.7 7. Kernel context and process context

Checkpoint 1 needs two saved continuations:

kernel context
    ↕
switch_context
    ↕
process context

When the kernel first switches to the process, the kernel context is saved.

When the process later yields, the process context is saved and the kernel context is restored.

When the kernel resumes the process, the reverse happens again.

The kernel context is not being introduced here as a second user process. It is simply the state needed so kernel code can continue after control returns from the process.

For CP1, this is not yet a user/kernel privilege boundary.

3.8 8. Starting a context that has never run

A previously running context already has a saved continuation.

A new process does not.

We solve that by constructing an initial context whose values make the normal restore mechanism enter a bootstrap function:

sp → top of the process's new stack
ra → process_bootstrap

Suppose the process has stack storage:

uint8_t stack[4096];

Because the stack grows downward, its initial stack pointer begins near the top of that storage.

The exact alignment details can be handled by provided code or a helper. The important idea is that the process owns separate stack storage and that the saved context points into it.

3.9 9. The bootstrap returns us to ordinary C

A small bootstrap can conceptually look like:

static void process_bootstrap(void)
{
    current->entry();
    process_exit(0);
}

The first restore enters this function because the initial context contains its address in ra.

From there, ordinary C function calls can be used.

This is an important pattern for the course:

Assembly is used only at the narrow boundary where the abstraction needs direct machine control. Once the boundary has been crossed, ordinary C and higher-level operating-system concepts take over.

3.10 10. Trace a complete cooperative switch

Assume the kernel is running and a new process has:

process.context.sp → its stack
process.context.ra → process_bootstrap

The kernel calls:

switch_context(&kernel_context, &process.context);

The switch:

  1. saves the kernel continuation and stack;
  2. restores the process context;
  3. executes ret;
  4. enters process_bootstrap.

Later the process calls:

process_yield();

Inside that operation, the process context is saved and the kernel context is restored.

The switch then returns to the kernel continuation saved by the earlier switch.

When the kernel later restores the process context, execution resumes inside the previous call to process_yield(). That function then returns normally, and the process continues after its yield.

This is what “resume” means in the first process implementation.

3.11 11. From saved context to first process

A saved context answers:

Where and with which machine state can execution continue?

Checkpoint 1 needs one slightly larger abstraction:

struct process {
    struct context context;
    uint8_t stack[4096];
    void (*entry)(void);
    enum state state;
    int exit_status;
};

This is one useful teaching representation, not a required internal design.

The process adds:

  • an entry function;
  • owned stack storage;
  • lifecycle state;
  • an exit status.

No scheduler, address space, or user-mode boundary is required.

3.12 12. Minimal lifecycle

A small lifecycle is enough:

unused
   ↓ create
ready
   ↓ run
running
   ↓ yield
ready
   ↓ run
running
   ↓ exit
finished

The distinctions are semantic:

  • create prepares an executable context but does not run it;
  • yield pauses a process that may run again;
  • exit finishes a process that must not run again.

3.13 13. Creation prepares the initial context

Creation establishes:

entry function
process stack
context.sp → top of that stack
context.ra → process_bootstrap
state → ready

The entry function itself has not executed yet.

The first run uses the same context-switch operation that later performs resume.

This is why the artificial initial ra and sp matter: they make a never-before-run process satisfy the same restore interface as an already-paused process.

3.14 14. Yield and resume

Suppose the process body is:

first_part();
process_yield();
second_part();

Yield means:

running → ready
save process context
restore kernel context

The kernel may perform other work and later run the same process again:

ready → running
save kernel context
restore process context

The restored continuation returns into the old process_yield(), which then returns normally. Execution proceeds with second_part().

No scheduler is required yet. Kernel code can explicitly decide to run the one process again.

3.15 15. Exit

Exit has different semantics:

process_exit(42);

means:

running → finished
exit_status = 42
restore kernel context
do not resume this process again

The saved context may still physically exist. The process abstraction determines whether the operating system is allowed to use it.

This distinction between machine capability and OS policy becomes more important later.

3.16 16. The full CP1 behaviour

The first checkpoint can now be described completely:

create
→ run on own context / stack
→ yield
→ kernel regains control
→ resume
→ exit with status
→ kernel regains control

All concepts required by that sequence have been introduced by the end of Lecture 3.

Lecture 4 therefore serves as consolidation, diagnosis, and transfer rather than adding another required mechanism immediately before the earliest checkpoint.

3.17 17. Key ideas

Students should leave this chapter able to explain:

  • why execution cannot resume unless relevant machine state survives;
  • why the stack pointer and separate stack storage matter;
  • how normal calling conventions reduce the state needed at a cooperative switch boundary;
  • why ra can serve as the cooperative continuation;
  • how a small assembly switch saves one context and restores another;
  • how an artificial initial ra and sp start a context that has never run before;
  • how a context becomes a process by adding entry, stack ownership, lifecycle state and completion information;
  • why create, yield, resume and exit are different operations;
  • why the assembly boundary can remain small while the process abstraction itself is built mostly in C.
