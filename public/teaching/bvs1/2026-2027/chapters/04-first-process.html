4  I Have a Process: Integration and Diagnosis

Wintersemester 2026/2027

Author
Affiliation

Stavros Kousidis

ICCT

All concepts required for the first checkpoint have already been introduced before this chapter.

The purpose here is different:

Can the complete mechanism be reconstructed, explained, and diagnosed without following a recipe?

This is the final consolidation step before:

CP1 — I have a process.

4.1 1. Reconstruct the dependency chain

The first process depends on several layers that were introduced separately:

source code
   ↓
RV64 executable
   ↓
machine execution
   ↓
saved execution context
   ↓
separate stack
   ↓
process lifecycle
   ↓
observable yield / resume / exit

The lower layers are still real, but the process abstraction lets ordinary reasoning move upward.

A useful distinction is:

  • machine-level mechanism — saved registers, stack pointer, return address, context switch;
  • operating-system abstraction — process state, lifecycle, entry, completion status.

4.2 2. Reconstruct the minimum process

Without relying on one required source-code layout, a first process must answer:

  • where can execution continue?
  • which stack belongs to it?
  • what code should it run?
  • may it run again?
  • how did it finish?

A saved context answers only the first question and part of the second.

The broader process abstraction owns the stack storage, identifies the entry function, records lifecycle state, and retains an exit status.

4.3 3. Reconstruct the lifecycle

The intended CP1 lifecycle is:

unused
   ↓ create
ready
   ↓ run
running
   ↓ yield
ready
   ↓ run / resume
running
   ↓ exit
finished

Creation prepares but does not execute.

Yield means the process may continue later.

Exit means the process is complete and must not resume.

This distinction must remain true even if a stale saved context still physically exists in memory.

4.4 4. Trace first run

A fresh process has an artificial initial context:

sp → top of its own stack
ra → process_bootstrap
state = READY

When the kernel switches to it:

  1. the kernel context is saved;
  2. the process context is restored;
  3. the final return uses the restored ra;
  4. the bootstrap begins on the process stack;
  5. ordinary C process code starts.

The initial continuation was constructed during process creation rather than saved from previous process execution.

4.5 5. Trace yield and resume

Suppose:

puts("A\n");
process_yield();
puts("B\n");

A correct observable trace can include:

A
<kernel output>
B

This demonstrates that the process continued after the yield.

A trace such as:

A
<kernel output>
A

suggests restart or reinitialization rather than resume.

At yield:

RUNNING → READY
save process context
restore kernel context

At resume:

READY → RUNNING
save kernel context
restore process context

The restored return address eventually lets process_yield() return normally.

4.6 6. Trace exit

If the process calls:

process_exit(42);

the required semantics are:

RUNNING → FINISHED
exit_status = 42
kernel regains control
process is not run again

The exit status is an observable completion result. It will later become useful when higher-level mechanisms such as a shell start processes.

4.7 7. Diagnose by concept

4.7.1 Wrong stack

Symptom:

process runs
process yields
kernel performs work
resume crashes or corrupts state

If the restored continuation looks plausible, investigate the process stack and saved sp.

A correct continuation on the wrong stack is still an invalid execution state.

4.7.2 Restart instead of resume

Expected:

process: first
kernel: back
process: second

Actual:

process: first
kernel: back
process: first

Likely conceptual causes include:

  • the yielded continuation was not restored;
  • the process was recreated/reinitialized before the second run.

4.7.3 Finished process runs again

If the kernel observes FINISHED and then resumes the same process, the lifecycle abstraction has been violated.

The lower-level context-switch mechanism may still be physically capable of restoring the saved registers. The OS abstraction must prevent that operation.

4.8 8. Function call versus process

Compare:

hello();

with:

create hello
run
yield
kernel work
resume
exit
kernel observes status

The second case has independently resumable execution state.

Useful distinguishing properties are:

  • separate stack storage;
  • saved continuation;
  • suspension without unwinding the call chain;
  • explicit lifecycle state;
  • observable completion status;
  • operating-system control over when execution continues.

A particular function name or file structure is not what makes it a process.

4.9 9. Why assembly is already disappearing

At the machine boundary, the implementation still needs operations such as:

save registers
restore registers
ret

But above that boundary the useful vocabulary is now:

create process
run process
yield
resume
exit

This is intentional.

The course is climbing an abstraction hierarchy. Once the mechanism below an abstraction has been understood, students should be able to reason with the abstraction without repeatedly expanding it into assembly.

They must still be able to descend one layer when explanation or diagnosis requires it.

4.10 10. CP1 behavioural contract

A public checker should eventually establish behaviour equivalent to:

process starts
process yields
kernel regains control
process resumes
process exits with a known status
kernel observes completion

The checker should observe behaviour rather than enforce one private source-code architecture.

Passing an output checker alone is not evidence of understanding. At the mandatory checkpoint, each student must also explain the mechanism and handle a small equivalent variation, prediction, or diagnosis.

4.11 11. Readiness questions

Before the checkpoint, a student should be able to answer without following a recipe:

  1. What state survives a yield?
  2. Why does the process need its own stack?
  3. How does first start differ from resume?
  4. Why is exit not another yield?
  5. How can output demonstrate resume rather than restart?
  6. Which narrow assembly mechanism supports the higher-level C abstraction?
  7. What would you inspect first if resume fails after kernel code has run?

These questions stay inside the announced competence family.

4.12 12. Bridge to the next problem

With one process, the kernel may explicitly decide when to run it again.

Now suppose:

process A never yields
process B is ready

If A keeps the CPU forever, B cannot progress.

That creates the next operating-system requirement:

How can the OS regain control when the running process does not cooperate?

Timer events, preemption and scheduling belong to the next phase, not to CP1.
