7  Scheduling Several Processes

Winter Semester 2026/2027

Author
Affiliation

Stavros Kousidis

ICCT

Lecture 6 gave the OS control at every tick, whatever the process does. With one process, the handler had only one frame to return. This chapter adds a second process and asks again: must the handler return the same frame? It does not. Returning a different frame is all that scheduling is, and the trap path of Lectures 5 and 6 stays exactly as it was. What the OS needs in addition is a record of its processes, a state for each of them, a rule for the choice, and an answer for the moment when no process may run.

Our running example is the spinner of Lecture 6, created twice. Neither process ever yields, so every switch you will see is a decision of the handler at a tick. In Exercise 6 you write that decision yourself; with Checkpoint 2 you write the whole OS around it.

7.1 Where we stand

7.1.1 The open question of Lecture 6

Lecture 6 ended with this picture of one process and a timer:

              OS             CPU               Process
                          +--------+
os_run()     | arm, MTIE  |        |
os_start()   +----------->| return |----------->| (start)
                          |        |            | loop ...
trap_entry   |<-----------|  trap  |<-----------+ timer
             | save frame |        |
trap_handler | re-arm     |        |
os_start()   +----------->| return |----------->| (resume)

os_run() arms the timer and enables it, os_start() returns into the process, the timer forces a trap, trap_entry saves the process’s registers into its frame, the handler re-arms the timer, and os_start() restores the same frame. The OS has control at every tick. Must it give the CPU back to the same process? With one process the question has only one answer.

7.1.2 Two spinners, neither yields

main() now creates two processes. Both run the spinner of Exercise 5: count to 1,000,000, print the counter, exit with status 7. They differ only in the name they print.

process_create(&p1, spinner_a);   /* prepared, not run */
process_create(&p2, spinner_b);   /* prepared, not run */
os_run();                         /* starts spinner A */

Nothing runs between the two process_create() calls: each call only prepares a frame. os_run() then starts the first process of the table, spinner A. The beginning of the recorded run, in our build (GCC 13.2, QEMU 8.2, -icount shift=4,sleep=off; the addresses are left out):

os: starting 2 processes
spinner A: start
os: tick 1 ... in process 1
spinner B: start
os: tick 2 ... in process 2
os: tick 3 ... in process 1

Tick 1 interrupted spinner A. The next line, spinner B: start, is printed by spinner B, which had never run before. So the handler did not return the frame of the interrupted process: it returned B’s prepared first frame. At tick 2 it returned A’s frame, and A continued exactly where tick 1 had stopped it, until tick 3 interrupted it again.

7.1.3 Which frame does the handler return?

Lecture 6: timer -> CPU -> OS -> the same frame    (one process)
Lecture 7: timer -> CPU -> OS -> which frame?      (several)

There is no new trap mechanism in this chapter. The trap path, the trap frame and the timer branch are those of Lectures 5 and 6. Everything new happens in the C code of trap_handler(), between the save and the restore: how the OS chooses the frame it returns, and what it needs to know for that. With this chapter the mechanism of Checkpoint 2 is complete.

7.2 The process table

7.2.1 A process that does not run is a saved frame

After tick 1, spinner B runs and spinner A waits. Where is A?

registers (CPU)    spinner B's state, live
p1.frame           spinner A's state, saved at tick 1
p2.frame           out of date while B runs

Every process owns one trap frame, a field of its struct process (Lecture 5). While a process runs, its state is in the CPU registers, and its frame holds the state of its last trap. While it does not run, its frame is all there is of it, together with its stack in memory. In particular, A’s pc is in p1.frame.pc: the trap pc of tick 1, an instruction of A’s counting loop that has not executed yet. The timer branch adds nothing to it (Lecture 6), so A executes that instruction first when it continues.

At tick 2, trap_entry saves B into p2.frame, and the handler returns &p1.frame. Returning another frame is therefore no new mechanism: os_start() restores whatever frame the handler returns. What is new is that the OS must know which frames exist and which of them it may return.

7.2.2 What the OS knows about each process

struct process {
    process_entry_t entry;       /* where it starts    */
    uint8_t stack[STACK_SIZE];   /* its own stack      */
    struct trap_frame frame;     /* how it continues   */
    enum process_state state;    /* may it continue?   */
    int exit_status;             /* how it ended       */
};

This is the process.h of Exercises 4 to 6: the bricks of Lecture 3, with the trap frame of Lecture 5 in place of the CP1 context. Each field answers one question of the OS: entry at the first start, stack for the process’s own function calls, frame for the return into it, state for the decision, and exit_status after the end. Nothing in the object is new. New is that the OS keeps several of them, and that it consults state to choose.

7.2.3 The process table and the current process

The process table is the OS’s record of all processes it manages. In the reference implementation it is an array of pointers, together with two more pieces of OS state:

static struct process *process_table[MAX_PROCESSES];
static unsigned int process_count;
static struct process *current_process;
process_table[0] -> p1   spinner A   "process 1"
process_table[1] -> p2   spinner B   "process 2"
current_process  -> the one whose frame was returned last

The table holds pointers: the struct process objects live where main() declared them, as static objects (Lecture 5, “Why p must become static”), and the OS records where they are. process_create() appends to the table, and the position in the table, counted from 1, is the number in every os: line. current_process is the process the CPU executes when the next trap comes; the handler needs it to know whose frame trapped and whose state to update. Real systems allocate their entries dynamically and keep them in lists or trees. For Checkpoint 2, a small fixed array filled at start-up is enough.

7.2.4 process_create() enters, it does not run

process_create(&p, entry)
    p.frame.pc      = process_start
    p.frame.regs[2] = stack top          (sp)
    p.state         = READY
    process_table[process_count++] = &p

This is Lecture 5’s “First entry: prepare a frame” plus one line, the table entry. After main()’s two calls there are two prepared frames, both READY, and nothing runs. os_run() chooses the first process, marks it RUNNING and calls os_start() with its frame, which restores it and executes mret. As in Lecture 5, the first start of a process is a return into a prepared frame. os_run() is the only place where a choice is made without a trap; from then on, every choice happens inside trap_handler().

7.3 States and transitions per event

7.3.1 Three states: which frames may be returned?

The lifecycle states of Lecture 3 now decide which frames the handler may return:

State Meaning Its frame
READY may run, waits for the CPU saved; may be returned
RUNNING executes on the CPU now out of date; the registers hold it
FINISHED has exited or faulted must never be returned

Exactly one execution is RUNNING: the one whose frame was returned last. With one process, the state was bookkeeping. With several, it is the input of the decision.

7.3.2 One transition per event

Every entry into the OS after start-up is a trap, and every trap is one of three events. Each event changes the state of the current process exactly once:

Event Cause (mcause) The current process
tick timer interrupt RUNNING -> READY
exit system call: ecall, number SYS_EXIT in a7 RUNNING -> FINISHED
fault other, e.g. illegal instruction RUNNING -> FINISHED

Then, in every case, the OS makes its choice: one READY process becomes RUNNING. Every trap ends one turn and starts the next.

Exit is a system call, as in Lecture 5: process_exit(status) executes ecall with the number SYS_EXIT in a7 and the status in a0. The CPU traps with mcause 11, which says only that an ecall happened; the handler reads a7 from the saved frame to find out which system call it was. Exit and fault have the same effect on the state and differ in the exit status. A tick is the only event that leaves the process READY: it may continue later.

There is no yield in Exercise 6 and Checkpoint 2. Lecture 6 moved from the cooperative to the preemptive case: a process now leaves the CPU when it exits or faults, or when the timer takes the CPU away. A yield would be a READY transition like the tick, with the +4 of every ecall on the trap pc. There is also no transition out of FINISHED, and no state for a process that waits for something; such a state is not part of Checkpoint 2.

7.3.3 The states as a diagram

process_create()          chosen
    -->  +-------+  ---------------->  +---------+
         | READY |                     | RUNNING |
         +-------+  <----------------  +---------+
                           tick             |  exit, fault
                                            v
                                       +----------+
                                       | FINISHED |
                                       +----------+

Only the handler and os_run() move a process from READY to RUNNING. Two arrows cannot be caused by the process itself: the tick, caused by the timer, and “chosen”, decided by the OS. The process causes its exit on purpose and a fault by mistake. Since Lecture 6, no process stays RUNNING for longer than one time slice.

7.3.4 Where the transitions happen in the handler

Lectures 5 and 6 ended the branches of trap_handler() with return reschedule(); (timer) and return finish_current(...); (exit, unexpected trap). Their bodies are the transitions of the table above:

static struct trap_frame *reschedule(void)   /* tick */
{
    current_process->state = READY;
    return next_frame();
}

static struct trap_frame *finish_current(int status)
{                                            /* exit, fault */
    current_process->exit_status = status;
    current_process->state = FINISHED;
    return next_frame();
}

The first part of each helper is the event’s transition of the current process. next_frame() is the choice: it asks the scheduling decision, schedule(), which process runs next, marks that process RUNNING, makes it the current process and returns its frame. next_frame() is a name for this text; the reference writes the same steps as switch_to(choose_next()). At Checkpoint 2 you write these functions yourself.

7.3.5 Never return a FINISHED frame

After spinner A’s exit, its frame still looks perfectly restorable:

p1.frame.pc  -> the instruction after the exit ecall
p1.state     =  FINISHED

The handler added 4 at the exit ecall, as for every ecall, so os_start() would restore this frame without complaint. Returning it would give the CPU back to a process that has ended. Neither the CPU nor the provided assembly knows about states; only the OS’s C code does, and that is why the state exists. The Exercise 6 library checks every choice and halts, for example with:

os: schedule() returned process 1 in state FINISHED, halting

7.4 Choosing the next frame: round robin

7.4.1 Scheduling: choosing the frame to return

Lecture 6 separated interrupt handling from the scheduling decision. With several processes, the state transition becomes a step of its own:

Step Who What happens
interrupt handling CPU, trap_entry the OS gets control
state transition trap_handler() the event changes the current state
scheduling decision schedule() a READY process is chosen
return os_start(), mret its frame continues

The scheduler is the part of the OS that makes the scheduling decision. In our OS it is one function, called at the end of every trap and once in os_run(). In Lecture 6 it had one candidate; now it has several, and the rule is ours to choose. The mechanism does not depend on the rule: any function that returns a READY process gives an OS that never restores a FINISHED frame. Which rule is a good one is a separate question.

7.4.2 Round robin: the next READY process after the current one

table:    [ p1 ]  [ p2 ]  [ p3 ]  [ p4 ]
                    ^
                 current
search:             p3 -> p4 -> p1 -> p2

Round robin: search the process table in order, starting after the current process and wrapping around at the end; the first READY process runs. Every READY process gets its turn in table order, like the players at a table. The current process comes last in the search, so it is chosen again only if no other process is READY. If there is no current process of the table, at the first start or after the idle process ran, the search starts at the first entry. If no process is READY at all, nobody from the table runs.

With the picture: if p2 is current, p3 and p4 are FINISHED and p1 is READY, then p1 runs. If only p2 is READY, p2 runs again.

Why start after the current process and not at the start of the table? Exercise 6 answers this question from a run.

7.4.3 The scheduling decision as one C function

In Exercise 6 the decision is a C function of its own, declared in the provided scheduler.h:

struct process *schedule(struct process *const table[],
                         unsigned int count,
                         struct process *current);
  • table[0] to table[count - 1] are the processes in creation order;
  • current is the process that just ran, already READY (tick) or FINISHED (exit, fault), or NULL if no process of the table ran: at the first start and after the idle process;
  • it returns a READY process of the table, or NULL if nobody is READY.

schedule() changes no state. It only answers the question “who runs next?”. The transitions, the re-arm of the timer and the frames belong to the OS around it: in Exercise 6 to the provided library, at Checkpoint 2 to your own code. That split keeps the decision testable on its own, and the same function works in both.

7.5 When nobody is READY: the idle process

7.5.1 Which frame after the last exit?

After os: process 2 exited 7, both entries of the table are FINISHED. The timer still fires every 10 ms, and the handler must return a frame, because os_start() restores one and mret continues it. The question arises already at the exit itself: finish_current() for the last process has to return a frame. Four answers come to mind, and none of them works:

Proposal Why not?
return a FINISHED frame an ended execution would continue
wait inside the handler mstatus.MIE = 0 there: no timer interrupt is taken
halt the machine the OS would end; CP3 needs it to keep running
return to main() main() has no frame: it is never resumed (Lecture 5)

The second row needs a closer look. The handler runs with interrupts off (Lecture 5, “On a trap: interrupts off”). A loop inside it would never be interrupted by the timer; the timer request would stay pending, and the handler would never return. Only interrupts are masked: an exception, such as an illegal instruction, would still trap inside the handler. Waiting therefore has to happen outside the handler, in an execution that runs with interrupts on.

In Checkpoint 2 nothing can become READY again after the last exit, so halting would look the same from outside. But the OS is the program that stays in control. From CP3 on, a shell waits for input, and processes that wait for an event are the reason why the case “nobody is READY” matters at all.

7.5.2 The idle process: a frame that waits

The handler needs a frame that may always run and does nothing:

static void idle_entry(void)
{
    for (;;) { __asm__ volatile ("wfi"); }
}

wfi (wait for interrupt) is a RISC-V instruction: the CPU may rest until an interrupt is pending. C has no word for it, so it is written as inline assembly. The loop goes around it because wfi may also return early.

The idle process has its own stack and frame, prepared in os_run() like the first frame of any process. It is not in the process table: it is never chosen by the rule and never finishes, and the scheduler only sees real processes. When schedule() returns NULL, the OS returns the idle frame. The idle process runs with interrupts on, because os_start()’s mret turns them on as for every process, so each tick enters the handler as usual. The Exercise 6 library prints no os: tick line for ticks in the idle process. The idle process has been visible since Lecture 5, after the last exit; this chapter explains why it must exist.

7.5.3 The whole run: who runs, who decides

The recorded run of the two spinners, one row per trap, after a first row for the start-up:

On the CPU Event The OS returns Why
(start-up) os_run() spinner A first READY
spinner A tick 1 spinner B next READY
spinner B tick 2 spinner A next READY
A, B, … ticks 3 to 16 B, A, … next READY
spinner A exit spinner B only READY
spinner B exit idle nobody READY
idle tick idle nobody READY

Each row is one transition, one decision and one frame. The end of the recorded output, in our build:

os: tick 16 at 0x800002be in process 2
spinner A: done, counter = 1000000
os: process 1 exited 7
spinner B: done, counter = 1000000
os: process 2 exited 7
os: all processes finished
os: 16 timer interrupts

Both spinners finish with exactly 1,000,000: each was interrupted eight times, and no increment was lost at any of the switches. The time slice is the period of the timer, not a budget per process: the OS re-arms the timer only in the timer branch, so after spinner A’s exit, spinner B gets only the rest of the current time slice. Whether that is fair is a question for Lecture 8.

7.6 Outlook: scheduling is more than taking turns

7.6.1 When, where, how

A scheduler answers more than one question:

Question Decides In our system
When? which process runs next, how long round robin at every tick
Where? on which core one CPU: nothing to decide
How? at which speed, in which power state full speed; wfi when idle

In this course we deal only with “when?”: our QEMU machine has one CPU, and our OS has no efficiency goal. What is “best” depends on the goal of the system: equal shares for servers and desktops, short response times for interactive programs, deadlines for control loops or audio (in real-time systems a late result is a wrong result), low energy for phones, laptops and data centres, limited temperature for passively cooled devices. The goals conflict: the fastest response costs energy, and the lowest energy costs time.

7.6.2 Schedulers in current systems

System When? Where? and How?
Linux EEVDF (since 6.6), real-time classes Energy Aware Scheduling, governors
Android the Linux scheduler Energy Aware Scheduling
Windows 11 priorities 0 to 31, round robin QoS levels (Eco: efficient cores)
macOS, iOS XNU Clutch: thread groups, QoS Edge: performance, efficiency cores
FreeBSD ULE (default since 7.1) per-CPU queues, topology-aware

Each of them combines a “when?” rule with mechanisms for “where?” and “how?”. Linux’s EEVDF selects the eligible task with the earliest virtual deadline and aims to give runnable tasks of the same priority equal CPU time; its real-time classes (SCHED_FIFO, SCHED_RR, SCHED_DEADLINE) serve tasks with timing requirements. Energy Aware Scheduling uses an energy model of the CPUs to place tasks on systems with cores of different capacity; frequency and idle governors choose the speed and the idle state. Windows schedules threads by priorities 0 to 31, round robin among the threads of the highest priority; its quality-of-service levels influence which cores a thread may use and how much power the processor spends. Apple’s XNU kernel schedules groups of threads with the Clutch scheduler and extends it with the Edge scheduler to clusters of performance and efficiency cores. FreeBSD’s default scheduler is ULE. These names and versions change; they are as documented in November 2026.

7.6.3 Crossover: electrical engineering

The power of a CMOS processor, simplified:

\[P = \underbrace{\alpha\, C\, V^2 f}_{P_{\mathrm{dyn}}} + P_{\mathrm{static}} \qquad\qquad E = \int_0^T P(t)\,\mathrm{d}t\]

A chip is built from transistors whose inputs, together with the wires between them, act as tiny capacitors. Whenever a signal changes from 0 to 1, such a capacitance is charged to the supply voltage \(V\); when it changes back, it is discharged. Charging a capacitance \(C\) to \(V\) draws the energy \(C V^2\) from the supply, and all of it ends up as heat. \(C\), the switched capacitance, is the capacitance of all nodes that can switch; \(\alpha\), the switching activity between 0 and 1, is the fraction of it that actually switches per clock cycle; \(f\) is the clock frequency. Together they give the dynamic power \(P_{\mathrm{dyn}}\). The static power \(P_{\mathrm{static}}\), mostly leakage, is paid as long as the core is on. The energy \(E\) is the power summed over the running time \(T\).

A higher \(f\) needs a higher \(V\), so the power grows faster than the frequency. Lowering both is called dynamic voltage and frequency scaling (DVFS). But a lower power does not mean a lower energy: a slower core runs longer, and pays the static power all that time. Run fast and then idle in a deep sleep state (“race to idle”), or run slowly? The answer depends on the chip.

7.6.4 Crossover: mathematics

A goal of the system can be written as an objective function under constraints, for example:

\[\min\; \Big( w_E\, E + w_W \sum_i W_i + w_R \sum_i R_i \Big)\]

\(E\) is the energy, \(W_i\) the waiting time of task \(i\) (the time it is READY but not RUNNING) and \(R_i\) its response time (the time from its arrival until it runs for the first time). The weights \(w_E\), \(w_W\), \(w_R\) express the goal, and the constraints (deadlines, fairness, number of cores, temperature) decide which schedules are allowed at all. On a phone, the response time of the thread that redraws the screen after a touch counts a lot, the waiting time of a background synchronisation hardly, and energy a lot, because the battery is the limit. In an audio system, the next buffer must be complete before the sound card plays it: that deadline is a constraint, and a small response time keeps the latency low.

The two crossovers work together: the hardware model gives \(E\), the goal of the system gives the weights. Linux’s Energy Model, for example, describes the power of each group of cores at each available frequency, and Energy Aware Scheduling uses it to estimate the energy of placing a task on one core or another. The objective function is a model, not an algorithm; choosing the speeds of tasks with deadlines so that the energy is minimal is a classical research problem.

7.6.5 Crossover: online optimisation

The objective above still hides most of the problem. It does not yet say in which order the tasks run, whether a task may be interrupted (preemption), whether it may move to another core (migration), or that power states change over time while the tasks run. And an operating system normally does not know when the next task will arrive or how long it will run.

Scheduling is therefore an online optimisation problem: the decisions must be taken during operation, on the basis of incomplete information. An offline algorithm, which sees the whole input in advance, can serve as a benchmark: how good could a schedule have been, had the future been known? For the theoretical solution of such problems, several kinds of methods come into question:

Method Suited for
exhaustive search exact solution of very small problems
integer linear programming offline optimisation
constraint programming complex constraints
dynamic programming suitable structured subproblems
greedy algorithms fast local decisions
heuristics practical online scheduling
reinforcement learning experimental adaptive scheduling

Round robin is a heuristic in this sense: it decides at every tick from the current state alone, quickly and without any knowledge of the future. It optimises nothing explicitly; it guarantees every READY process its turn.

7.7 Our trap model: who does what, with the scheduler

Step Who What
request CLINT pending while mtime >= mtimecmp
trap CPU if enabled: mepc, mcause; interrupts off; pc <- mtvec
save trap_entry registers and trap pc into the current frame
transition trap_handler() the event changes the current process’s state
decide scheduler a READY process, else idle
restore os_start() registers and mepc from the chosen frame
return CPU, mret pc <- mepc; interrupts on

Compared with Lecture 6, the “decide” row splits into the transition and the decision, and the save and restore rows name “the current frame” and “the chosen frame”. Nothing in the hardware rows changed since Lecture 6, and nothing in the assembly rows since Lecture 5. The model stays restricted: machine mode only, one interrupt source, no nested traps, no privilege separation, and no state for a process that waits for an event.

7.8 Key ideas

  • Process table: the OS records every process it manages. A process that does not run is its saved frame.
  • States: READY, RUNNING, FINISHED. Every event (tick, exit, fault) changes the state of the current process once; then the choice makes one READY process RUNNING.
  • Scheduling decision: which READY frame the handler returns, kept apart from interrupt handling. A FINISHED frame is never returned.
  • Round robin: the next READY process after the current one, in table order, wrapping around.
  • Idle process: the frame the handler returns when nobody is READY; it waits with wfi and interrupts on.
  • With this, the CP2 mechanism is complete: trap, save, transition, decide, restore, return.
  • Scheduling in real systems answers “when?”, “where?” and “how?” for goals such as real time or energy; electrical engineering and mathematics supply the models. Because the future is unknown, it is an online optimisation problem, solved in practice by heuristics such as round robin.
